## 1. The rule this must not break

Reading the model IDs from config must not change which model runs, or the ID that is logged, anywhere (D-235 item 4).

- **The defaults equal the strings that run today:** `claude-sonnet-5` for extraction and `claude-haiku-4-5` for routing. Neither literal has changed since it was added (`eb76329`, 2026-09-16; `cc810e6`, 2026-09-25).
- **No environment sets either setting:**
  - CI has no `.env`.
  - The Fly images don't copy `.env`, and neither `fly.toml` `[env]` block sets them.
  - The founder ran `fly secrets list` on `docflow-api-staging` and `docflow-worker-staging` on 2026-11-12: neither sets them.
  - The founder deleted both lines from the local root `.env` on 2026-11-12. Until then it set `DOCFLOW_ROUTING_MODEL=claude-haiku-4-5-20251001`, which would have changed the routing ID on every local run once wired.
  - No Windows user or machine variable sets them.

So every process gets the defaults, which are today's strings.

**Pushback, for the founder (Q1): remove `SESSION_SECRET`.**
- Nothing will ever read it, because sessions are Supabase Auth's.
- `.env.example` tells a developer to generate a long random secret "used to sign session cookies". That is untrue, and it puts a secret on machines where nothing uses it.
- Removing it means deleting the `config.py` line and the `.env.example` lines. Parse's self-test keeps the name in its list of names a job must not hold, which costs nothing.

`STRIPE_PUBLISHABLE_KEY` and `API_BASE_URL` also have no planned reader, but they hold no secret. Leaving them, with the comment saying so, is harmless.

## 3. The price table and the load-time check

**In `packages/core/docflow_core/config.py`, the only file with model-ID literals afterwards:**

```python
EXTRACTION_MODEL_DEFAULT = "claude-sonnet-5"   # verified 2026-09-16; Section 3
ROUTING_MODEL_DEFAULT = "claude-haiku-4-5"     # verified 2026-09-25 (D-141)

@dataclass(frozen=True)
class ModelPrice:
    input_usd_per_million: Decimal
    output_usd_per_million: Decimal

# Not environment variables. Exactly the models that run, at today's prices
# (the same figures extraction.py:88-93 holds now).
MODEL_PRICES = {
    EXTRACTION_MODEL_DEFAULT: ModelPrice(Decimal("2.00"), Decimal("10.00")),
    ROUTING_MODEL_DEFAULT: ModelPrice(Decimal("1.00"), Decimal("5.00")),
}
```

- **The settings:**
  - `docflow_extraction_model: str = EXTRACTION_MODEL_DEFAULT`
  - `docflow_routing_model: str = ROUTING_MODEL_DEFAULT`
- **The check:** a `model_validator(mode="after")` on `Settings`. It raises if either configured model isn't a key of `MODEL_PRICES`. The message names the setting, the value, the IDs the table holds, and the fix ("add the model and its price to MODEL_PRICES in the same PR, and re-run the golden set").
- **It runs when Settings loads.** So `get_settings()` fails the same way in the API, the worker, the scripts (`record_example_fixtures.py`, `measure_long_order.py`) and the tests.
- **Q2, for the founder: should a model also be held to its role?** The table check alone lets `DOCFLOW_EXTRACTION_MODEL=claude-haiku-4-5` through, because it is in the table. Section 3 forbids the cheaper model for final extraction.
  - I propose a `role` field on each entry (`extraction` or `routing`), with the check refusing a model configured outside its role.
  - That is beyond what you specified, so it is a question, not a plan.

**In `packages/core/docflow_core/extraction.py`:**
- `EXTRACTION_MODEL` and `ROUTING_MODEL` stay as module names, so their readers don't change: `model_runs.py`, the two scripts and the tests. They are set from `get_settings()` once, at import.
  - That is the same lifetime as today's constants.
  - The tests that clear the settings cache never set a model setting, so nothing a test does can change them.
- **The four `_..._COST_PER_TOKEN` literals and their two comments (lines 87-93) go.** `_cost`, `extraction_input_cost`, `routing_input_cost` and the routing call's cost read `MODEL_PRICES[...]` for the model in use, divided by one million. They produce the same `Decimal` values as today.

**Startup lines (founder's answer 1):**
- **API:** one line at start, at warning level like `api_docs_off`, so it reaches Fly's log: `model_ids: extraction=claude-sonnet-5 routing=claude-haiku-4-5`. A Settings error at import is caught and printed as `DocFlow API refused to start: ...`, as the CORS and parse-token refusals are.
- **Worker:** `run_workers.main` prints the same line beside `dispatch_in_flight_target=` (RUNBOOK 9.2 reads that one).
  - `in_flight_target_refusal` re-raises any settings error that isn't its own. So `main` catches the model error first and prints `run_workers refused to start: ...`, not a traceback.
  - Beat makes no model call and prints nothing new.

**`.env.example`:**
- The two lines are commented out: `# DOCFLOW_EXTRACTION_MODEL=` and `# DOCFLOW_ROUTING_MODEL=`.
- A note above them: "Leave unset. The defaults in config.py are the pinned models, and a model not in MODEL_PRICES stops the app at start (D-239)."

## 4. `model_runs.py:188`: how lost calls are priced today (founder's question 4)

`close_lost_runs` writes the outcome row for a call whose worker died (D-163).

**How it prices that row today:**
- **An extraction row** is priced only when its `model_id` equals `EXTRACTION_MODEL`, at the extraction price. Any other model gets tokens only, with no cost ("a model this code doesn't price any more").
- **A routing row** is priced at the routing price whatever its `model_id` says.

**Is it a bug?** It is an inconsistency that can't show today, because no figure is wrong. The routing literal has been `claude-haiku-4-5` since routing began (`cc810e6`, 2026-09-25), so every real routing row carries that ID. It would become a wrong figure the day the routing model changes: a routing call lost under the old model would be priced at the new model's price.

**The fix I'd propose** (not in this PR without the founder's answer, Q3): price every lost row by its own `model_id` through `MODEL_PRICES`.
- Extraction rows get the extraction price.
- Routing rows get the routing price.
- An ID not in the table gets tokens only, for both kinds.

Today that gives the same costs. Two worker tests write routing results with stand-in IDs (`"routing-model"`, `"m"`, `apps/worker/tests/test_parse_and_extract.py:557,943`). I would check whether any of them reaches `close_lost_runs` before changing it.

**This PR doesn't touch `model_runs.py`.** Its import of `EXTRACTION_MODEL`, `extraction_input_cost` and `routing_input_cost` is unchanged.
