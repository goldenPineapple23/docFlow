## 1. The backfill

**What it does.** It finds every document whose `page_count` is NULL and queues
`docflow.render_pages` for it on the `pages` queue. That is the same task, queue and
process a new document uses (D-232), so there is no second pipeline. Everything after the
queueing is A3's code as merged: the original's hash is checked; pages are drawn by the
parse service in its sandbox; the list is written once, first write wins; stale keys are
deleted; and a failure is best effort with no alert.

**How it is started: a command run on the worker machine.**
`python -m app.backfill_pages [--dry-run] [--batch N] [--limit N]`, started under a Grant
with `fly ssh console` at plan task 7, after the parse and worker deploys. It is
documented in RUNBOOK 9.2, and each run is recorded there.

Why this over the alternatives:
- **A Console action** would need a cross-tenant `adminDataAccess` path, an
  `admin_actions` row, a screen and its tests: about a day more, for a run that happens
  once on staging and once on production.
- **A beat job** would keep re-queueing documents whose render fails for good, such as a
  file the parse service refuses. Stopping that needs an attempt count, which means a
  migration.
- **On the worker machine** the command uses the worker's own login and broker. No key
  leaves the app, and nothing is run from this PC against staging.

**Which documents.** `page_count IS NULL`, `deleted_at IS NULL`, the tenant not
`pending_deletion` or `deleted`, and status `needs_review`, `approved`, `exported` or
`rejected`, which are the statuses a reviewer opens.
- **Left out:** `pending`, `staged` and `processing`, because the live pipeline queues
  their render itself.
- **Left out:** `quarantined`, which is never parsed (D-232 item 12).
- **Left out:** `failed`, which has no review screen to show pages on. Its original
  either failed the parse service already or never reached extraction.
- **Never selected (founder, 2026-11-11):** a `quarantined`, `failed` or `processing`
  document is never selected, whatever its `page_count`. A test proves that a
  quarantined document with `page_count` NULL is not queued.

Test-batch documents are included, since they are reviewed like any other. Oldest first,
by `created_at` and then `id`.

**Bounded, so live work isn't starved.**
- Documents never wait on it: they have their own process and slot (D-232 item 2).
- It queues at most `--batch` renders (default 3, at most 10), then waits until the
  `pages` queue's length is 0 before queueing the next batch. It reads that length the
  way the Console's strip does.
- So a new document's render waits behind at most one batch, which is seconds on real
  files. The worst case is the 15-minute limit per render (D-232 item 7).
- `--limit` stops after N documents, for a first small run.

**Idempotent and resumable.** The command keeps no state of its own: the database is the
state.
- A second run selects only what is still NULL.
- If a live render and a backfill render of one document overlap on the one pages
  process, the second one finds the list written and stops (`pages_skipped
  reason=already_drawn`).
- One pages process at concurrency 1 stays the only safe configuration (RUNBOOK 9.2;
  D-232 item 2). The backfill adds no process.
- A document whose render fails is queued once per run, never in a loop.

**Output.** Counts and IDs only (Section 7.10):
- `--dry-run`: the count of documents per tenant ID that would be queued, and nothing is
  queued.
- A run: `backfill_pages queued=N` for each batch.
- At the end: `backfill_pages done queued=N`. The last render may still be running
  then, so the command doesn't count what is still not drawn itself: `--dry-run`, run
  again once the pages queue is empty, gives that count. The failures are already in
  the logs as `pages_failed document_id=… error_type=…` (D-232 item 5).
- If the queue doesn't empty within `--max-wait` seconds (default 1,800, two renders'
  hard limit), the run stops with a non-zero exit and a line asking whether the pages
  process is running.

**Tenant scope (Section 7.5).**
- Tenants are listed through the worker's narrow tenant-listing session, which can read
  tenant IDs and nothing else (migration 0027).
- Each tenant's documents are read in that tenant's own `tenant_session(tid)`.
- Each task carries the `tid` from that session, and `render_pages` re-checks everything
  in `tenant_session(tid)`.
- Storage paths go through `read_file` and `save_page`, which enforce
  `tenants/{tid}/`.
- **See question 1:** today a guard and a record allow only the stuck sweep to use that
  session.

**Sections 7.9 to 7.11.**
- **7.9:** the batching above; no new alert, under D-232 item 5's ruling.
- **7.10:** IDs, counts and error types only.
- **7.11:** the backfill opens no file. Every render runs in the parse service's sandbox,

## 3. `DISPATCH_IN_FLIGHT_TARGET` on the worker app

**Today.**
- It is read in one place, `Settings.dispatch_in_flight_target`
  (`packages/core/docflow_core/config.py:145`), with a default of 1. Three things use it:
  - Celery's `worker_concurrency` (`celery_app.py:130`);
  - the `documents` process's `--concurrency` (`run_workers.py:66`);
  - the dispatcher's free slots (`dispatch.py:151`).
- **Missing:** the default, 1, which is what `PARSE_SLOTS = 2` was sized for.
- **Not a number:** the settings fail to load and the machine doesn't start, with a
  traceback rather than a clear line.
- **0 or below:** nothing refuses it. `--concurrency=0` makes Celery start one process
  per CPU, and the dispatcher sees no free slots. That is a real gap.
- **2 or more:** it starts. It oversubscribes the parse service's two slots, so jobs
  fail to get in and retry. The CI guard (`test_ci_guards.py:138`) can't see a value set
  as a Fly secret.

**Proposed** (see question 2):
- **(a) Log it.** `run_workers` prints `run_workers: dispatch_in_flight_target=N` at
  start, beside the login check line. The deploy step at task 7 reads it from `fly logs`,
  which is read-only. Fly can't show a secret's value otherwise.
- **(b) Log it and refuse anything else.** In addition to (a), `run_workers` refuses to
  start, the way it refuses a foreign login (`run_workers.py:114`), when the value isn't
  the default the CI guard checked against `PARSE_SLOTS`. It also refuses a value that
  isn't a whole number of at least 1. The refusal line names D-232 and RUNBOOK 9.2.
  Raising capacity then means changing the default and `PARSE_SLOTS` together, which is
  what RUNBOOK 9.2 already asks.

**RUNBOOK.** It is a setting, not a constant, so it stays out of 9.6's table. 9.2 step 1
gains the start line and, with (b), the refusal.

**Catalog.** None. Like the foreign-login refusal, this is a founder-facing start line,
and no tenant sees it.

**Tests.** `apps/worker/tests/test_run_workers.py` (or the existing worker start tests):
- the line is printed;
- with (b): refused for 0, 2 and "two"; started for 1;
- the refusal reads the same default that `test_ci_guards.py` checks.

## 4. `image_preview`: a proposal only, nothing built

**What it is.** For TIFF and HEIC only, the parse service makes one image of the
original:
- `apps/parse/parse_service/parsing/documents.py:262`, used at `:355`;
- checked by `parse_client.py:227`;
- stored by the worker as a `converted_image` preview (`parse_and_extract.py:107-160`).

Text previews (`extracted_text`) are a different thing and are not touched.

**What reads it.** The API, when a TIFF or HEIC has no drawn pages:
- `review.py:939-942` shows the frame;
- `review.py:1086` serves the preview's bytes into it.

Tests: the parse service's baseline and parity tests, `test_parse_client.py`, and two
entries in `test_broad_except_guard.py`.

**What would break if it retired.**
- A TIFF or HEIC whose pages aren't drawn would show the download panel instead of the
  page. That covers a render that failed or was cut off.
- It also covers a new document opened before its render finishes. The render is queued
  beside extraction (D-232 item 1), so a fast reviewer can get there first.
- The frame is its only reader. The frame's removal waits until after the demo (D-235
  item 11).

**Agreed (founder, 2026-11-11): keep it until after the demo,** and decide it with the
frame's removal (D-235 item 11), since
retiring it is that decision's other half. Retiring it now saves no work in the demo and
removes the one in-page fallback for those two formats. Stored previews stay in Storage
either way.

**Size: 0.25 day** (this proposal and its reading).
