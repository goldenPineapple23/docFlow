## 1. What exists today

Read on `c57013e`.

- **The body is never read.** `email_intake.parse_postmark_payload` takes the sender, subject, Message-ID, headers and attachments. `TextBody` and `HtmlBody` are dropped, so `raw_emails` holds no body.
- **An e-mail without an attachment is refused** as INT-001 before any other check (`evaluate_email`, `process_inbound_email`).
- **Nothing links a document to its e-mail** except the `message_id` text both rows carry.
- **`extraction_runs.document_id` is `NOT NULL`,** and the daily cost breaker sums runs through a join to `documents` (`usage.daily_ai_spend`). A model call about an e-mail that has no document yet has nowhere to be recorded.
- **HTML is read as text (carry item 38; slice 2).** The parse service gains an HTML reader, so an `.html` file and an HTML-only `.eml` reach extraction as text, not markup (D-235 item 13).
- **The parse service already reads `cid:` references** in an `.eml`'s HTML (`_cid_references`), for the uploaded-file path. That helps the pilots half, not this one.
- **The ignored-mail list** is `GET /ignored-mail`: the last 100 `intake_rejections` rows from e-mail, each with its catalog entry.
- **The viewer has a `text` view** that shows the text DocFlow stored from a document, escaped (Section 7.12's clarification).

## 2. How a body becomes a document

The rule is D-230 item 4's: the body is labelled first, and it becomes a document only if the label says so or can't be trusted. A cover note never gets a `documents` row.

### 2.1 At the webhook (the API; nothing is parsed here)

1. `parse_postmark_payload` also reads `TextBody`, `HtmlBody` and `Date`, as strings. No HTML is parsed or cleaned in the web process (Section 7.11).
2. **Which body is kept as "the body":** `TextBody` when it has any non-blank character, otherwise `HtmlBody`. Question 1 covers an e-mail whose text part is only a stub.
3. **It is stored in Storage** through `save_file`, as `E-mail text.txt` or `E-mail text.html`, under the tenant's prefix like any received file. The bytes are exactly what the sender wrote. The path, kind, size and SHA-256 go on the `raw_emails` row.
   - When both parts exist, the HTML part is stored too, as a second object, so the raw e-mail is complete (Section 7.2). Only the chosen one is read.
4. **The gate order is unchanged,** with one new input, "has a body":
   - Message-ID dedupe; the address not active (INT-005, INT-006); the rotated address (INT-008): all as today.
   - No attachment **and a blank body**: INT-001, as today.
   - The ceilings, the attachment cap, authentication, the sender allowlist, unknown-sender velocity: as today, and they now also apply to an e-mail with a body and no attachment (section 6).
5. **Attachments are handled exactly as today.** Each accepted one is a document, and its row now carries `raw_email_id`.
6. **A non-blank body of an e-mail that was not held** is marked `pending` on its `raw_emails` row. After the transaction commits, one task is sent: `docflow.label_mail_body(tenant_id, raw_email_id)`.
7. The webhook still answers 200 for every handled outcome.

### 2.2 The labelling task (the worker)

One attempt, no retries of its own, and every failure ends in "make it a document" (D-230 item 4).

1. Read the body from Storage and check its hash.
2. **Send it to the parse service** (`parse_client.parse_document`), which returns text. For `.txt` that is the decoded text. For `.html` it is the new HTML reader's output (section 3). The body is never opened in the worker.
3. Build the model's input: one text part with `Subject:`, `From:` and `Date:` taken from the `raw_emails` row, then the body's text. All of it goes inside the document delimiters, so the subject is untrusted data too (Section 7.2).
4. Keep that text as the body's stored text (`raw_emails.body_text_path`, a derived object). **What the reviewer is shown is exactly what the model read.**
5. **One call to the routing model** (`claude-haiku-4-5` from M10's config, its existing price; D-235 item 4). Structured output, strict schema:
   - `label`: `order`, `change`, `cancellation`, `quote_request`, `status_question` or `not_an_order`;
   - `label_confidence`: 0 to 1;
   - `contains_order_lines`: true or false. The prompt defines an order line as an item and quantity the sender is ordering with this message. Items in a quote request, in a question about an earlier order, or in "don't order yet" are not order lines;
   - `order_lines_confidence`: 0 to 1, the confidence item 4 reads (D-230 item 9);
   - `injection_suspected`: true or false.
   - The input is cut at a new constant, `MAIL_LABEL_TEXT_CHAR_BUDGET` (proposed 12,000 characters). **A body that was cut counts as below the threshold,** because order lines may be past the cut.
   - A `started` row is committed in `extraction_runs` before the call and an outcome row after it, as D-163 has it, with `run_kind = 'mail_label'` and `raw_email_id`.
6. **The decision is one pure function in core,** `mail_labels.decide_body(...)`. The body becomes a document when any of these holds:
   - `contains_order_lines` is true;
   - `order_lines_confidence` is below `MAIL_LABEL_REVIEW_THRESHOLD`;
   - `injection_suspected` is true;
   - the call failed, timed out, or returned output that doesn't validate;
   - the body was cut, or the parse service couldn't return its text.
7. **If it becomes a document:** one transaction inserts the `documents` row (`source = 'email'`, `email_part = 'body'`, `raw_email_id`, `storage_path` = the stored body, its hash, `pending`), runs the same duplicate check as an attachment, records the label on `raw_emails`, and records the allowance thresholds. Then the dispatcher is nudged. From there it is an ordinary document: the normal pipeline, the normal review screen, counted against the allowance.
   - `injection_suspected` from the label is carried onto the document so it is forced to review with the banner, whatever extraction says later.
8. **If it doesn't:** the label is recorded on `raw_emails`. An ignored-mail row is written when the e-mail produced no document at all, or when the label is `change` or `cancellation` (D-230 item 5's demo-half ruling). Its code is the new INT-012, and it carries the label.
9. **If the task itself is lost** (the worker dies): the stuck sweep finds a body `pending` for longer than `STUCK_PROCESSING_TIMEOUT_MIN` and makes it a document without a call. Nothing waits unseen.

### 2.3 The body document in the pipeline

- `parse_and_extract` is unchanged except for one step: for a document with `email_part = 'body'`, the `Subject`, `From` and `Date` part is put in front of the parse service's parts, through the same helper the labelling task uses. So extraction reads the PO number from a subject like "PO BM-26-3317".
- Extraction's system prompt, schema and model are unchanged. Their hashes don't move, and a test asserts it. **No golden re-run is needed for B1** on Section 7.1's terms. The labelling prompt is new and has its own tests (section 9).
- No approved-example change: a body document picks examples by sender exactly as an attachment does.

### 2.4 What the viewer shows

- **A body document:** the existing `text` view, showing the stored text, escaped. No page images are drawn for it. The original's download gives the stored `.txt` or `.html` as a file, never opened in a tab.
- **Every document from an e-mail** (body or attachment) gets an "E-mail" panel on the review screen: sender, subject, received time, the body's text (escaped, scrollable), and the body's label with its confidence as a plain label ("Cover note", "Order", "Quote request" ...). For a body document the panel shows the header and label only, since the text is already in the viewer.
  - Served by one new read, `GET /review/documents/{id}/email`, tenant-scoped through `documents.raw_email_id`. The Console reaches it through acting-as, like the rest of the review screen.
  - While the label is still pending the panel says so. If the body's text couldn't be read, the panel shows a catalog message (section 5).
- **The review queue** marks a body document "From the e-mail's text".
- **The ignored-mail list** shows each row's label, and a row opens to show the body's text, escaped.
- Nothing from a body is ever rendered as HTML, and no image in it is ever fetched.

### 2.5 HTML-only bodies

- The stored original is the sender's HTML, untouched.
- The parse service turns it into text (section 3). That text is what the model reads, what the viewer shows, and what is kept for approved-example prompting.
- The same reader fixes carry item 38 for an uploaded or attached `.html` file and for an HTML-only `.eml`: D-235 item 13's "no raw markup reaches extraction" then holds on every path.

### 2.6 Forwarded and quoted chains

- **Nothing is stripped.** The whole body goes to the label call and to extraction. In a forwarded order the lines are in the quoted part, so removing quoted text would remove the order.
- **A new warning, VAL-019,** is raised on a body document when the text has a forwarded or quoted block. It is found with fixed patterns, no model call: `-----Original Message-----`, `Begin forwarded message`, an `On ... wrote:` line, a `From:` / `Sent:` / `Subject:` header block inside the body, or lines starting with `>`. It changes no value and must be acknowledged at approval like any warning (Section 7.3, 7.7).
- A forwarded e-mail attached as a file (`message/rfc822`) arrives as an attachment and is unwrapped by the parse service as an `.eml` is today, one level deep.
- The reply to a held thread ("Re: PO 1877, when will it ship?") that quotes the old order below it is the hard case for the label. The prompt's definition of an order line covers it, and anything the model is unsure of goes to review.

## 3. Untrusted text and HTML

- **Where HTML is read:** only in a parse-service job: sandboxed, no network, memory and time limits, one file per process (Section 7.11). Never in the API, never in the worker.
- **The reader:** Python's standard `html.parser`, so no new dependency and nothing that resolves an entity file or a URL.
  - Dropped with their contents: `script`, `style`, `head`, `template`, `noscript`, `svg`, `object`, `embed`, `iframe`, comments.
  - Kept as text: everything else. Block elements and `<br>` end a line. A table row becomes one line with its cells joined by `, `, as the DOCX and XLSX readers do.
  - Links keep their text and lose their address. Images contribute nothing.
  - **Text hidden by CSS is kept** (question 2). The reader doesn't evaluate styles, and the rule in 2.2 step 4 means the reviewer sees it too.
  - A nesting-depth cap and the job's time limit stop a hostile file. A file that hits them is answered as today's parse failures are.
- **`.html` and `.htm` resolve to the HTML type** in `file_types.validate_upload`, by extension among the text-like formats, which is the rule its own comment states and doesn't apply. Slice 2 also answers carry item 38's second half: whether `previews.py`'s HTML entry is reached today.
- **Prompt injection:**
  - The body, and the subject line with it, sit inside the document delimiters in both calls.
  - The label call's system prompt says the content is data, and its schema has `injection_suspected`. True forces a document, and that document is forced to review with the banner.
  - Body text is never put into SQL, a path, a shell command, a log line, or any other prompt. Logs carry IDs, sizes, the label and the confidence only (Section 7.10). The label is one of six fixed words.
- **Size limits:**
  - A body is stored whole. Over `MAX_FILE_SIZE_BYTES` (25 MiB, the existing cap) it is refused with the existing size code as an ignored-mail row.
  - The label call reads at most `MAIL_LABEL_TEXT_CHAR_BUDGET` characters; a cut body becomes a document.
  - Extraction reads a body document under the limits every text document has today.
- **Abuse:** each labelled body is a paid call of roughly a fifth of a cent, so the body path gets the same defences as documents (section 6): the cost breaker, the ceiling, authentication, the allowlist, and the velocity rule, which now counts unknown senders' labelled bodies as well as their documents.

## 6. The sender allowlist and `MAIL_LABEL_REVIEW_THRESHOLD`

**The order is: gate first, label second.** A held e-mail is never sent to the model (Section 7.16.3), so the allowlist always wins over the label.

- **Strict sender mode (the demo tenant; D-235 item 16).** An e-mail from a sender not on the list is held as `sender_not_allowed`, as today.
  - Its attachments are quarantined as today.
  - Its body is stored and marked `held`. No label call is made.
  - **A held e-mail with a body and no attachment** gets one quarantined `documents` row for the body, so it appears in the Held list and the Console's quarantine list and can be cleared there. Without it, a body-only e-mail from an unlisted sender would be invisible.
  - On the demo tenant nothing held is released, so a held body never reaches the model.
- **Releasing a held e-mail (any tenant):**
  - A released body document goes straight to extraction with no label call. A person has decided it is real, which is D-230 item 6's "a person can send one to extraction".
  - When an attachment's document is released and its e-mail's body is `held`, the body is sent to labelling then (question 5).
- **The other holds** apply to a body-only e-mail in the same way: the cost breaker and the abuse ceiling (with INT-007's reply), an authentication failure, and unknown-sender velocity.
- **The attachment cap** counts attachments only. The body is never counted as an attachment, so "11 attachments quarantines all 11" is unchanged.
- **Known senders:** unchanged. A body document counts toward "this sender has a prior document" like any other.

**The threshold.**

- `MAIL_LABEL_REVIEW_THRESHOLD = 0.80`, defined once in `docflow_core.constants`, listed in RUNBOOK with the other constants, and logged with the decision.
- It is read by one function, `decide_body`, against `order_lines_confidence` only.
- **My reading of items 4 and 5 together,** for the founder to confirm (question 3):
  - `order_lines_confidence` decides whether the body becomes a document (item 4).
  - `label_confidence` never makes a document on its own. A quote request or status question with a low label confidence, and no order lines at or above the threshold, goes to the ignored-mail list with its label (item 5's demo-half ruling).
- The value is checked against the PO set's e-mails once they have run live (D-230 item 4): the report lists each e-mail's two confidences beside its answer key.
- The attachments half of item 4 (skipping) is not built here.

## 11. Questions for the founder

Each has my recommendation. Nothing is built until they are answered.

1. **Which part is read when an e-mail has both text and HTML?** Recommended: the text part, unless it has less than half the HTML part's visible characters, in which case the HTML part. A stub text part ("view this in an HTML reader") beside a full HTML order would otherwise be labelled "not an order" with high confidence and the order missed. The comparison costs one extra parse job for e-mails with both parts.
2. **Text hidden by CSS in an HTML body: keep or drop?** Recommended: keep. The reviewer then sees everything the model read, and Section 7.2's defences apply to it. Dropping needs a CSS evaluator in the reader, and any gap in it would hide text from the reviewer that the model still saw.
3. **Two confidences, read as section 6 says?** Recommended: yes. `order_lines_confidence` alone decides whether a body becomes a document; `label_confidence` is stored and shown and decides nothing in the demo half.
