Governing text: `docflow-mvp-features.docx` (Account and operations), `CLAUDE.md`

## What a customer can do today (verified in code)

| Have | Where |
|---|---|
| The review queue (needs review / approved / rejected / exported / failed / all) | `/review`, `GET /review/documents` |
| Review one order: edit, approve, reject, mappings, warnings, original document | `/review/[id]` |
| Export (CSV, Excel, JSON, IIF), history, "Approve & export" | inside the review screen |
| Held documents, release, ignored mail | `/held` |
| Allowance banner and held notice (dismissible), company name in the header | Purchase orders list, header |
| Roles on write routes (`require_reviewer`: owner, admin, reviewer may change things; viewer reads) | API |

## What is missing (found while reading)

1. **No customer-facing upload.** `POST /documents/upload` exists and is
   hardened, but no customer page calls it. "Upload PO" is the first line of the
   MVP feature list. Today a customer can only get orders in by email.
2. **No tenant dashboard.** Nothing shows documents by status or recent activity.
   The spec also puts the "Held for review" count on it (7.16.4).
3. **No "needs review" email.** No template, no trigger.
4. **No way for an owner or admin to add or manage users.** Section 3 says every
   user after the first is "invited by a tenant owner/admin", but the only
   invite that exists is the founder's, for the first user. A customer cannot
   add a reviewer.
5. **No tenant-wide audit log.** Each order has its own trail; there is nothing
   that answers "what happened in our account this week".
6. **Roles are enforced on the API's write routes, but nobody has audited every
   tenant route against the role table**, and the UI does not consistently
   explain a refusal.

## Proposed shape: four parts, a check-in after each (like 5.4)

### 5.8a — Home, navigation and upload
- A **Home** page (`/`) that is the tenant dashboard: counts of documents by
  status, "needs review" oldest age, this month's use against the allowance,
  the held-for-review count and reason in plain English (catalog wording), and
  recent activity (last 10 events). Live counts scoped to the tenant with the
  existing status indexes; no scan of history and no cross-tenant read.
- The header gets real navigation: Home · Purchase orders · Held for review ·
  Upload · (Team, Activity for owner/admin).
- **Upload** page: choose one or more files, the same upload endpoint and error
  catalog as any other path (no second handler, Section 10), per-file result
  ("received", or the catalog reason it was refused, or "held" with the
  catalog reason). Viewers cannot upload.
- Sign-in lands on Home.

### 5.8b — Team and roles
- **Team** page for owner and admin: list users (name/email, role, status),
  **invite** a user (the same DocFlow-generated invite and outbox path the
  founder uses), change a role, deactivate. Rules enforced in the API:
  only an owner can create or demote an owner; the last owner cannot be removed
  or demoted; an admin cannot change an owner; nobody changes their own role.
- A **role audit**: a table of every tenant route against owner / admin /
  reviewer / viewer, with a test that walks the route table and fails if a
  route is missing from it (so a new route cannot ship unclassified).
- The UI hides what a role cannot do and, when an API refusal happens anyway,
  shows the catalog message (`AUTH-002` style), not a bare error.

### 5.8c — Activity (audit log)
- **Activity** page for owner and admin: one chronological, cursor-paged log of
  key actions in the account: approvals, rejections, edits (counts, not
  values), exports, releases and clears of held documents, mapping and rule
  changes, invites, role changes, deactivations, address rotation. Rows the
  founder made while supporting the account are labelled **DocFlow support**
  (7.15.1). Filter by action type and person.
- Written from the existing `review_actions`, `exports`, `documents.released_*`
  and `tenant_lifecycle_events` where they exist, plus a new small
  `tenant_audit_events` table for the actions that have no home yet (user
  changes). Values from documents are never shown in the log, only that an edit
  happened and where to click through (Section 7.10).

### 5.8d — Email notifications
- "A document needs review" email to the people who review (see question 3).
  Uses the outbox and a template in the repo; wording from the catalog rules.
- Per-person on/off is **not** built (that is preferences beyond the MVP list);
  the owner can choose who is a reviewer by role.

## Migrations
Expected: `0022` — `tenant_audit_events` (tenant_id, RLS from creation), a
`users.deactivated_at`-style field only if `is_active` does not already cover it,
and a `notification_state` row per tenant for the email throttle. Applied to
staging by hand, as before.

## Tests I would write
- Every tenant route classified by role, with a route-table walk (5.8b).
- A viewer/reviewer/admin/owner matrix on the team actions, including the
  last-owner and self-demotion refusals.
- Tenant isolation for every new list: Tenant B's users, activity and counts
  never appear for Tenant A.
- The dashboard's counts equal a hand-written query for a seeded tenant.
- Upload through the page hits the same validation and quarantine gate as email.
- The audit log never contains an extracted value.
- The email throttle: a 500-document burst produces a bounded number of emails.
- Browser tests for each new screen; a real-stack drive at the end.

## Questions for the founder

1. **Scope.** Is all of this right for 5.8? In particular: do you want the
   **Upload page** and the **Team page** now? Both are missing and both are
   things a customer will ask for in the first week, but neither is named in the
   phase-plan line, only implied by the feature list and Section 3.
2. **Landing page.** Should sign-in land on the new Home dashboard (my
   recommendation) or stay on Purchase orders?
3. **The "needs review" email.** A 500-document backfill must not send 500
   emails. Options: (a) **a digest** — at most one email per tenant every 15
   minutes ("12 documents need review"), to owner, admin and reviewers
   (recommended); (b) one email per document, capped; (c) a single daily
   summary. Which, and should viewers get it?
4. **Who sees Activity.** Owner and admin only (my recommendation), or
   reviewers too?
5. **Order of the four parts.** I would go a → b → c → d. Different order, or
   anything to drop?


## Founder decisions (2026-09-23)

1. **Upload page: yes**, added to scope. The founder's case: an order that arrives
   by mail or handwritten can be photographed and uploaded. Who may upload: owner,
   admin, reviewer (not viewer). Caveats to tell customers: handwriting will read
   poorly (expect low confidence and heavy review, so test a real sample before
   promising it); each photo is one document, so a multi-page order should be one
   PDF or multi-page TIFF; on a phone the button can open the camera.
2. **Sign-in lands on Purchase orders, "Needs review"** (unchanged), not on a Home page.
3. **"Needs review" email: a digest**, at most one email per tenant every 15
   minutes ("12 documents need review"), so a 500-document backfill cannot send 500
   emails. Recipients: owner, admin and reviewer; viewers not.
4. **Activity log** is visible to reviewer, admin and owner (not viewer).
5. **Dashboard** is for owner and admin only; reviewers land on their queue.
6. **Order of the parts: mine.** a) Upload, navigation and the dashboard,
   b) Activity, c) the review-digest email, d) the team piece if it is wanted. A
   small **role audit** (every tenant route classified against the role table, with
   a route-table test; no UI) goes with (a).
7. **Roles in practice:** every tenant has an owner (the first user, created with
   the tenant; the onboarding doc calls this person the "first admin") plus
   reviewers. No cap on reviewers: neither the pricing doc nor any spec mentions
   seats. The `admin` role stays in the database (Section 3 locks four roles) but
   no admin needs to be created until a customer has a manager who is not the owner.

## Still open

- **Team piece.** Section 3 says every user after the first is "invited by a tenant
  owner/admin", and nothing for that exists: today not even the founder can add a
  second user from the Console. Options: (A) a small Team page for owner and admin
  (list, invite a reviewer/viewer/admin, deactivate; no role editing, no billing);
  (B) a founder-only "Add a user" button on the Console tenant page; (C) nothing
  for now. Recommendation: A, or B if customer self-service is not wanted yet.
- **Admin from the Console.** Should the Console allow creating a tenant user with
  the `admin` role, or only owner and reviewer for now?
- **Dashboard contents.** Confirm: documents by status, oldest "needs review"
  age, this month against the allowance, the held count and reason, and the last
  10 events.
